# [0.2.0](https://github.com/kevin-lee/token-watchroo/issues?q=is%3Aissue%20is%3Aclosed%20milestone%3Am3) - 2026-11-02


The app now updates itself, and it has an About panel. Two faults that could leave the usage cards wrong or stopped are fixed. The envelope `version` stays 1, and the Foreign Function Interface (FFI) only gains an additive field.

## Upgrade from 0.1.x

**A copy older than 0.2.0 has no self-update, so it does not see this release by itself. Upgrade it one more time, with Homebrew or with the disk image. After that, the app updates itself.**

With Homebrew, run `brew update` first:

```bash
brew update
brew upgrade --cask token-watchroo
```

The cask now has `auto_updates true`, and an old Homebrew can skip such a cask. If the app stays on 0.1.x, run:

```bash
brew upgrade --cask --greedy token-watchroo
```

## New Features

### Self-update with Sparkle (#71)

The app uses [Sparkle](https://sparkle-project.org) to check for a new version at most once a day. It shows the release notes, downloads the update, and offers "Install and Relaunch". A new menu item, "Check for Updates...", is below "About Token Watchroo".

- **Verified updates.** Each update must have a valid EdDSA (Edwards-curve Digital Signature Algorithm) signature and the same Developer ID as the app. The feed is signed too. The app verifies an image before it opens it.
- **One feed per architecture.** Apple Silicon and Intel copies each get their own build.
- **Network use.** The app now also reads the update feed from GitHub at most once a day and on demand, and it downloads the disk image from GitHub when you choose to install. Sparkle's system profile is off. The app sends no usage data.
- **Homebrew.** `brew upgrade --cask token-watchroo` still upgrades a copy that is older than the cask, and leaves a copy that Sparkle already updated alone.

This release is the first with Sparkle, so the first real in-app update comes with the next release.

### About panel (#77)

"About Token Watchroo", above Quit, shows the full version, the licence, the project and author links, and the architecture of the build, including when it runs under Rosetta. The icon follows the appearance of the system.

## Bug Fixes

### Refreshes stopped until a restart (#83)

Scala Native 0.5.12's `SynchronousQueue` could throw a `NullPointerException` when an `offer` met a timed `poll` that had just timed out. This killed a cats-effect worker and the refresh on it, and the cards then stopped updating until the app was restarted. The library now carries a corrected copy of that file, pinned to Scala Native 0.5.12.

### Stale Codex usage from an old local log (#81)

With no Internet connection, the Codex card could show usage from an old local log as if it were current.

- A window whose reset time has passed is now expired. It no longer counts for the status, the ring or alerts.
- The local-log note shows the time of the event.
- Compressed rollout logs (`*.jsonl.zst`), which Codex writes after 7 days, are skipped and never decoded.

The FFI gains an additive `observedAt` field on `AgentSnapshot`.

### A build could produce an app that did not start (#87)

This affected local builds. No release is known to be affected, because a release builds from a fresh checkout.

A relink added to the existing static library, and old members stayed. Archives with stale members crashed or hung at launch, and they passed every check. Why a stale archive fails is not proved.

- The build removes the archive before a link when the class path contents or the native config changed.
- `stageNativeLib` fails on signs of stale members.
- The Build and Release workflows now start the app, and fail unless the app reports that the library started.

## For contributors

- The Scala Native optimiser is back on in release-fast (#20). The cause of the original problem is still a hypothesis.
- The build sets the garbage collector (GC) yieldpoint mode in the sbt server's own environment, so a server started without the variable still links with conditional yieldpoints (#72).
- The Build workflow keeps the GC log and the test processes' output after a test failure (#73).
- The Release workflow has a new `appcast` job, which signs the feeds, and the release secrets are in the `release` environment. The app's self-update needs `SPARKLE_ED_PRIVATE_KEY` there.
- sbt `2.0.10`.

## Install

### Homebrew (recommended)

```bash
brew install --cask kevin-lee/tap/token-watchroo
```

Already installed, see [Upgrade from 0.1.x](#upgrade-from-01x).

### Disk image

Download `Token-Watchroo-0.2.0-arm64.dmg` (Apple Silicon) or `Token-Watchroo-0.2.0-x64.dmg` (Intel) from the [Releases](https://github.com/kevin-lee/token-watchroo/releases) page, open it, and drag **Token Watchroo** to Applications. The builds are Developer ID signed and notarized.

## Known limitations

- The #44 workaround depends on a link-time variable: a build made without it carries the GC bug. The guards in `build.sbt` and in the workflows exist for that, and the official builds are verified with `nm`.
- On Intel, the forced-collection test `BridgeSpec` still fails in about one run in 20 with a `NullPointerException`, a crash at address 0, or a hang (#67). The cause is unknown. It has not been seen in the app, which never forces collections, but no Intel Mac was available to check the app itself.
- The Codex Enterprise spend response shape is unverified. If the real response cannot be decoded, Codex falls back to the newest rollout log and the card note says why.
- The usage endpoints are undocumented and may change.
- The app never refreshes tokens. When a token expires, run `claude` or `codex` once and the card recovers on the next refresh.
- No settings window. Thresholds are fixed at 80% and 95%, and the refresh runs every 60 seconds.
